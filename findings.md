# Standardized QA Readout Measures Memory-Pipeline Sensitivity Rather Than Native End-to-End Agent Behavior

Current counterfactual results should be interpreted as evaluating each agent's memory pipeline under a shared LongMemEval QA answer head, not as a pure measurement of the agent's native end-to-end response behavior. In the current setup, the agent-specific parts that remain native are memory write construction, memory updating, retrieval, provenance mapping, and write-time replay. However, the final answer is generated through a unified prompt and evidence formatting layer rather than each agent's original `get_response` prompt.

This design choice is useful and defensible because it removes prompt-style confounds across agents, makes outputs compatible with LongMemEval's QA format, and produces cleaner cross-agent comparisons of memory dependence. Without a shared answer head, observed differences would mix together memory quality, response style, verbosity, refusal behavior, formatting differences, and prompt-specific temporal reasoning instructions. With the shared answer head, the comparison is more directly about which memories each system stores, surfaces, and exposes to the final answer stage.

The main caveat is that time-shift effects, especially those involving timestamp manipulation and temporal validity, are not purely measuring each agent's native answer behavior. They measure whether temporally shifted memories, as surfaced by each agent's memory system, causally affect a standardized QA readout. In particular, if the unified answer prompt explicitly instructs the LLM to use timestamps and prefer temporally valid evidence, then part of the observed effect comes from the shared readout head rather than the native agent prompt.

For reporting, the safest description is: "counterfactual memory-pipeline audit with standardized QA readout." A less accurate description would be "native end-to-end agent evaluation." If questioned, the right methodological claim is that the experiment isolates memory effects by standardizing final answer generation, while preserving agent-specific memory construction, retrieval, and replay dynamics. This means the results are suitable for comparing memory-pipeline fragility and temporal sensitivity across agents, but they may under- or over-estimate what would happen under each agent's original response prompt.

Concrete example: a stronger real instance appears in the MemoryOS run for `question_id=gpt4_d9af6064`, a temporal-reasoning question asked at `2023/03/28 (Tue) 01:25`: "Which device did I set up first, the smart thermostat or the new router?" The baseline answer is correct: the unified answer head says the new router came first on January 15 and the smart thermostat came later on February 10. Two core memory items are present in the baseline prompt: one router write (`write_id=bc359466663237ee`, wrapper timestamp `2023-03-28 04:39:00`) whose content states that the user got a new router on January 15, and one thermostat write (`write_id=c6f20a815845ac38`, wrapper timestamp `2023-03-28 15:46:00`) whose content states that the user finally set up the smart thermostat on 2/10.

When the router write is time-shifted, the wrapper does not remove it from the MemoryOS replay. Instead, it rewrites the event timestamp and replays the full memory history. Under `timeshift_promote_before_query`, the router write is reassigned from `2023-03-28 04:39:00` to `2023-03-28 01:24:59`. Under `timeshift_demote_far_past`, it is reassigned to `2023-02-26 04:39:00`. In both cases, the router write is still present in `cf_retrieved_write_ids` and `cf_prompt_write_ids`, and the thermostat write is also still present in the retrieved and prompted evidence. So the counterfactual does not work by deleting the router evidence or by making the thermostat evidence newly appear. The core content remains visible at answer time.

Despite that, the final answer changes substantially. After shifting the router write to `2023-03-28 01:24:59`, the system answers: "You set up the smart thermostat first on February 10th." After shifting the same router write to `2023-02-26 04:39:00`, it answers: "You set up the smart thermostat first on February 10, 2023, before the new router acquired on January 15, 2023." This is exactly the kind of interference pattern that shows the current time-shift setup is not purely measuring native MemoryOS retrieval. The memory system still surfaces the relevant router and thermostat facts, but the standardized QA readout head sees different memory timestamps in the evidence block and changes how it interprets temporal validity and relative weighting.

This concrete case therefore sharpens the methodological point. The current experiment measures "agent-specific memory pipeline plus standardized temporal QA readout" rather than native end-to-end agent behavior. MemoryOS still determines what gets written, how replay changes the memory state, and which memory items are surfaced to the answer stage. But once those items are surfaced, the final temporal judgment is partly controlled by the shared answer head, which explicitly reasons over the rendered `date=...` fields. This is the right interpretation to use when presenting time-shift results.

# Strong Baseline Performance Can Coexist With High Counterfactual Fragility

One of the most useful empirical stories in the current slice is that strong baseline benchmark behavior does not imply robustness to memory intervention. In the runs analyzed so far, MemoryOS is clearly not a weak baseline system: the stored benchmark summary in `cf_compare_results/memoryos_original_accuracy.txt` reports `Accuracy: 0.5` on the 50-question slice, compared with `Accuracy: 0.2` for SHARE in `cf_compare_results/share_original_accuracy.txt`. At the same time, when we switch from benchmark accuracy to write-level counterfactual analysis on the `04_09_18_11` traces, MemoryOS has the highest query fragility rate among the currently usable agents: `0.66` for MemoryOS versus `0.58` for THEANINE, `0.16` for SHARE, and `0.08` for LD-Agent.

This combination is important because it argues against the naive interpretation that "less sensitive" automatically means "better." A system can look stable under rollback simply because it is not using memory deeply enough, or because it already abstains on most questions and therefore has little room to deteriorate further. That is exactly why the low-fragility agents need to be interpreted together with their baseline answerability. In the same `04_09_18_11` slice, the baseline `I don't know` rate is `0.38` for MemoryOS, `0.46` for THEANINE, `0.86` for SHARE, and `0.94` for LD-Agent. For LD-Agent in particular, `47/50` baseline answers are already `I don't know`, so its low aggregate influence and low fragility should not be read as clean robustness. There is simply much less headroom for rollback to flip an answer or push the system into abstention.

The better interpretation is that MemoryOS is more memory-grounded. Its stronger baseline performance appears to come from relying more effectively on surfaced memory, and that same reliance makes it more vulnerable when a causally important write is removed or shifted. In other words, the current evidence supports the statement that "high accuracy and high fragility can coexist when the accuracy is genuinely memory-supported." This is a stronger and more interesting story than saying MemoryOS is merely unstable. The point is not that MemoryOS performs poorly; the point is that its success appears to depend on specific memories strongly enough that counterfactual write-time replay can expose hidden failure points that benchmark accuracy alone misses.

Concrete example: on the `04_09_18_11` MemoryOS trace, `question_id=7e00a6cb` asks: "I'm planning my trip to Amsterdam again and I was wondering, what was the name of that hostel near the Red Light District that you recommended last time?" The baseline answer is correct: `International Budget Hostel`. Across the three rollback runs for this query, only one target write removal causes a collapse to `I don't know.`, while the other two rollbacks leave the answer unchanged. That single successful rollback is enough to make the query fragile (`query_fragile = 1`), and the per-run scores show why the query-level metrics matter: one rollback has `influence_score = 1.9681`, `answer_changed = 1`, `abstention_flip = 1`, and `answer_distance = 0.7`, while the other two rollbacks stay near zero influence. This is a concrete case where the system answers correctly in baseline, but a specific memory write is important enough that removing it destroys answerability. That pattern is exactly the hidden fragility that ordinary benchmark accuracy does not reveal.
